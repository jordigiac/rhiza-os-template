# Workspace shapes — reference for proposing structure

*Claude reads this when a client workflow needs a folder shape. Nobody
memorizes it. Jordi surfaces what repeats; Claude proposes; the client says
yes or no.*

**The one question that picks the shape: what is the repeating unit?**

| The repeating unit is… | Shape to propose |
|---|---|
| A run — same steps, new deliverable each time | Numbered step folders, each with a CONTEXT.md contract and an output/ the next step reads (the `_template/CONTEXT.md` pattern) |
| A record — a person, client, or deal that accumulates | One folder per record, every record stamped from the same template, plus a one-line-per-record index |
| The knowledge itself — a wiki, a reference body | Linked notes with a small index; always-needed pages separated from look-up-when-needed pages |
| Several run-types sharing one voice/brand | Each run-type gets its own workspace; the shared reference lives once, above them, linked down |
| A whole org — teams, processes, handoffs | Bigger clients only; map teams and processes as linked note cards. Talk to Jordi before proposing this |

**Rules that hold for every shape:**

- Don't build a workspace for work that's only happened twice — that's a
  skill or a saved prompt, not architecture.
- Stage boundaries go where the human naturally pauses to check something.
- Three real steps beat seven imagined ones. Start smaller than feels right.
- Each folder states its own job inside itself; the structure is the
  documentation.
